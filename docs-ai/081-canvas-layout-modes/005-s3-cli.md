# 081 / 005 — S3: `prowl canvas` CLI (#760)

## Context

Agents create several tabs with `prowl create tab`, but could not ask Canvas to lay them
out (#760). With S2, a layout is a mode Canvas keeps applying, so one CLI call is enough
to keep a fleet of agent tabs tiled.

## Change

- **Wire**: `Command.canvas(CanvasInput)` with `CanvasAction` (`show`, `hide`, `layout`,
  `fit`, `status`), an optional `CanvasLayoutName`, and `show` (for `layout`/`fit`).
  `CanvasCommandPayload` reports `action`, `showing`, `layout` (the remembered mode,
  absent until set), and `card_count`. Schema `prowl.cli.canvas.v1`
  (`canvasData` / `canvasResponse`); errors `CANVAS_NOT_SHOWING`,
  `CANVAS_UNAVAILABLE`, `CANVAS_FAILED`.
- **CLI**: `CanvasCommand` group with one leaf per action; one-line text rendering.
- **App**: `CanvasCommandHandler` works through three injected closures (state
  snapshot, perform, wait). `show`/`hide` toggle Canvas through the reducer and wait for
  the view switch. `layout`/`fit` require Canvas to be showing (or `--show`), send the
  existing `CanvasCommandRequest` (new `.fit` case), and wait until the Canvas view has
  taken it, so the response — and any following `status` — reflects the new mode. The
  status mode comes from `CanvasLayoutStore.storedMode()`, which works while Canvas is
  hidden.
- **Canvas view**: a request sent just before Canvas showed is fulfilled on appear
  (a new view sees no change event). A layout chosen before the viewport was measured is
  kept by the entry layout, because a remembered automatic mode always applies on entry
  (S2 review fix).
- Contracts (`docs-ai/013-prowl-cli/contracts/canvas.md`, `input.md`, `schema.md`), the
  user manual (`docs/components/cli.md`, `canvas.md`, `docs/README.md`), and the
  `prowl-cli` skill are updated together, per the four-layer rule of
  [060](../060-prowl-cli-targeting-and-contract-governance/000-plan.md).

## Review fixes

- The live wait polled with `try? clock.sleep`, so a cancelled request (the CLI hung up)
  spun the main actor until the timeout. `ProwlApp.pollUntil` now returns false on
  cancellation and is tested with a `TestClock`.
- A request Canvas never ran used to stay pending and run on the next entry. Canvas now
  drops its pending request when it closes (`dropCanvasCommandRequest`), and the handler
  reports success only when `lastPerformedCanvasCommandRequestID` matches its request, so
  a replaced or dropped request fails instead of reporting `ok`.

## Decisions

- **No implicit view switch.** `layout` and `fit` fail while Canvas is hidden unless
  `--show` is passed: an agent should not pull the person out of the view they are
  using without being told to.
- **One wire command with an action field** (like `tab`/`pane`), not one per action
  (like `agents.*`): one schema entry, one router slot, one error namespace.
- **Wait for the view.** View-local commands are fulfilled by `CanvasView`; the handler
  polls (50 ms, up to 3 s) until the request is consumed instead of returning "accepted".

## Verification

- `CanvasCommandParsingTests`, `CanvasSchemaTests`, and three socket round-trip tests in
  `ProwlCLIIntegrationTests` (JSON layout request, text status, error schema).
- `CanvasCommandHandlerTests` (status, idempotent show/hide, unavailable Canvas,
  `CANVAS_NOT_SHOWING`, `--show` ordering, fit, a request the view never takes),
  router/envelope tests, and `ProwlAppCLITests` wiring.
- Prowl Debug: in the normal view, three `prowl create tab` calls followed by
  `prowl canvas layout tile --show` switched to Canvas and tiled six cards; two more
  `create tab` calls re-tiled eight cards (4 + 4) with the newest focused; `status`, `fit`,
  `hide`, `CANVAS_NOT_SHOWING`, and `CANVAS_UNAVAILABLE` behaved as specified.
